# 自定选题候选（3 详 + 2 简）

> 前提：PostgreSQL 18 + Django 6.1 + AdminLTE 3.2（技术栈最终定案，见 `AGENTS.md` §1）；第 14 组 2 人；用户已明确“难度不是问题”。
> 所有候选均满足作业“自定题目”6 条要求：≥2 角色、5–10 个相互关联功能、≥5 张表、主外键与约束齐全、业务异常处理、多表+统计查询。
> 撰写日期：2026-10-29

## 0 结论

- **首选 A：实验室仪器设备预约与借用管理系统** —— 校园场景真实（川大实验室共享平台），约束最硬（时段排他 + 资产单元唯一占用），演示动线完整（预约 → 审批 → 领用 → 归还 → 维修 → 统计），2 人约 14 人日。
- **次选 B：停车场收费管理系统** —— 亮点是“费率规则建模 + 分段计费 SQL”，复杂度适中，演示有实时车位看板，2 人约 12 人日。
- **想要 SQL 最漂亮选 C：药房处方调配与药品批次管理** —— FEFO 先到期先出用窗口函数逐批分配，是全作业最好的 SQL 素材，但界面偏表单，2 人约 15 人日。
- 简版 D 健身房课包、E 考场排考：见第 4 节，D 工作量最小，E 约束最硬但界面最弱。

## 1 候选 A：实验室仪器设备预约与借用管理系统（推荐）

### 1.1 场景与背景（报告 1.1 素材）

高校大型仪器共享平台：设备单价高、数量少，学生/教师必须先预约时段再领用，超期或损坏要追责，管理员要管审批、维修与报废。现实痛点：微信群排期、纸质登记、设备冲突与逾期无人追。→ 系统把“时段”与“资产单元”都建成数据，冲突在数据库层就不可能出现。

### 1.2 角色（3 类）

| 角色 | 权限 |
| --- | --- |
| 学生 / 教师（申请人） | 浏览设备、按时段预约、查看预约状态、领用与归还、查看自己的违约记录 |
| 设备管理员 | 审批/驳回预约、发放与回收设备、登记维修与报废、查看逾期清单 |
| 系统管理员 | 维护设备类别、设备与资产单元、账号与角色 |

### 1.3 表设计（8 张）

| # | 表 | 关键字段 | 约束亮点 |
| --- | --- | --- | --- |
| 1 | `app_user` | username, real_name, role, department, phone | `username UNIQUE`、`role CHECK IN ('student','teacher','equipment_manager','admin')` |
| 2 | `instrument_category` | name, description | `name UNIQUE` |
| 3 | `instrument` | category_id, name, model, manufacturer, max_borrow_hours, deposit_amount | FK；`CHECK (max_borrow_hours > 0)`、`CHECK (deposit_amount >= 0)` |
| 4 | `instrument_unit` | instrument_id, asset_no, location, status | `asset_no UNIQUE`；`status CHECK IN ('available','reserved','in_use','maintenance','retired')` |
| 5 | `reservation` | unit_id, applicant_id, start_at, end_at, purpose, status, reviewer_id | **时段排他**（见 1.4）；`CHECK (end_at > start_at)`；`status CHECK IN ('pending','approved','rejected','cancelled','fulfilled')` |
| 6 | `borrow_record` | reservation_id, unit_id, borrower_id, borrowed_at, due_at, returned_at, deposit_status | **未归还唯一**部分索引；`CHECK (due_at > borrowed_at)`、`CHECK (returned_at IS NULL OR returned_at >= borrowed_at)` |
| 7 | `maintenance_record` | unit_id, type, start_date, end_date, cost, description | `type CHECK IN ('repair','maintenance','retirement')`、`CHECK (end_date >= start_date)`、`CHECK (cost >= 0)` |
| 8 | `violation` | user_id, borrow_record_id, type, points, fine_amount, handled | `type CHECK IN ('overdue','damage','no_show')`、`CHECK (points BETWEEN 0 AND 12)` |

### 1.4 数据库设计亮点（答辩主攻点）

```sql
-- 同一台资产单元的预约时段不得重叠（待审批与已批准都算占用）
ALTER TABLE reservation ADD CONSTRAINT ex_unit_time_overlap
    EXCLUDE USING gist (
        unit_id WITH =,
        tsrange(start_at, end_at, '[)') WITH &&
    ) WHERE (status IN ('pending', 'approved'));

-- 一台资产单元同时只能有一条未归还的借用记录
CREATE UNIQUE INDEX uq_unit_active_borrow
    ON borrow_record (unit_id) WHERE returned_at IS NULL;
```

- `'[)'` 半开区间：归还当天闭馆前再借出的边界不会误报冲突，报告里能用一段话讲清楚。
- “预约”与“借用”两张表分工：预约是**未来时段占用**，借用是**当前实物占用**，两者用 `borrow_record.reservation_id` 串起来 —— 报告 3.2.1 的 ER 图主线。
- 逾期不用冗余字段，用视图计算，避免数据不一致：

```sql
CREATE VIEW v_overdue AS
SELECT br.id, u.real_name, iu.asset_no,
       br.due_at,
       (CURRENT_DATE - br.due_at::date) AS overdue_days
FROM borrow_record br
JOIN app_user u ON u.id = br.borrower_id
JOIN instrument_unit iu ON iu.id = br.unit_id
WHERE br.returned_at IS NULL AND br.due_at < now();
```

### 1.5 功能清单候选（9 项）

1. 设备类别维护（增删改查）
2. 设备与资产单元管理（登记、状态变更、报废）
3. 设备检索与可用时段查询（按类别/名称/位置/时间段）
4. 时段预约提交（选择资产单元 + 起止时间，冲突即时提示）
5. 预约审批与驳回（管理员，状态流转）
6. 领用登记（预约转借用，设备置 `in_use`）
7. 归还与逾期结算（逾期天数、违约金、押金状态）
8. 维修与报废登记（设备置 `maintenance` / `retired`，维修期间不可预约）
9. 统计与预警（设备使用率 Top10、月度借用次数与收入、逾期清单、爽约率）

### 1.6 演示动线（5 分钟）

学生端：设备卡片列表 →（筛选类别）→ 选一台设备看可用时段 → 预约 → 我的预约显示"待审批"
管理员端：审批列表 → 通过 → 领用登记（设备变"借用中"）
学生端：归还（超期 2 天 → 提示逾期天数与金额，生成违约记录）
管理员端：维修登记 → 统计看板（使用率柱状图、月度借用趋势、逾期清单表）

### 1.7 SQL 任务示例（报告第 4 章 / 演示可跑）

- 查询某资产单元未来 7 天的已占用时段（`generate_series` 时间槽 + `LEFT JOIN reservation`）。
- 统计每类设备本月借用次数与押金总额（多表 JOIN + `date_trunc`）。
- 设备使用率 Top10（借用时长合计 / 可借用天数）。
- 查询逾期未归还清单及逾期天数（视图 `v_overdue`）。
- 查询"预约通过但未领用"的爽约记录（`reservation.status='approved'` 且无对应 `borrow_record`）。

### 1.8 工作量与风险

- 规模：8 表、3 角色、9 功能；估算 **14 人日**（后端 6 / 前端 5 / 数据与文档 3）。
- 风险：审批流与设备状态机要严格对应（预约通过 ≠ 设备被占用，只有领用才 `in_use`），需先画状态机图再写代码。

## 2 候选 B：停车场收费管理系统

### 2.1 场景与背景

校园/商场停车场：车位有限、按时长阶梯计费、月卡与临停并存、出入口需记录。痛点：人工收费易错、费率调整无据可查、车位实时状态不可见。

### 2.2 角色（3 类）

车主（临停/月卡）、收费员（出场结算、异常处理）、管理员（车场/车位/费率/月卡维护）。

### 2.3 表设计（8 张）

| # | 表 | 关键约束 |
| --- | --- | --- |
| 1 | `parking_lot` | name UNIQUE、`CHECK (total_spaces > 0)` |
| 2 | `parking_space` | `UNIQUE (lot_id, space_no)`、`status CHECK IN ('free','occupied','reserved','disabled')` |
| 3 | `vehicle` | `plate_no UNIQUE`、`type CHECK IN ('small','large','ev')` |
| 4 | `access_record` | **车位占用时段排他**；`CHECK (out_at IS NULL OR out_at > in_at)` |
| 5 | `fee_rule` | **费率规则时间区间不得重叠**；`CHECK (unit_price >= 0)`、`CHECK (free_minutes >= 0)` |
| 6 | `monthly_card` | **同车月卡生效区间不得重叠**；`CHECK (end_date >= start_date)` |
| 7 | `payment` | `method CHECK IN ('cash','wechat','alipay','card')`、`CHECK (amount >= 0)` |
| 8 | `app_user` | 收费员/管理员 |

### 2.4 数据库设计亮点

```sql
-- 一个车位同一时刻只能停一辆车（out_at 为空表示在场，区间上界为无穷）
ALTER TABLE access_record ADD CONSTRAINT ex_space_occupied
    EXCLUDE USING gist (
        space_id WITH =,
        tstzrange(in_at, out_at) WITH &&
    );

-- 同一车型同一时段的费率规则不得重叠（费率可调，历史可追溯）
ALTER TABLE fee_rule ADD CONSTRAINT ex_fee_rule_overlap
    EXCLUDE USING gist (
        vehicle_type WITH =,
        time_period WITH =,
        daterange(valid_from, valid_to, '[]') WITH &&
    );
```

- **费率规则建模**是最大加分点：单价不在代码里硬编码，而是存成带生效区间的规则表，改价只需插一行，历史账单仍可按当时规则复算 —— 报告里能写出"为什么不把单价写死在车位表"。
- 分段计费 SQL：时长 → 减去免费分钟 → 按日/夜时段拆分 → 套用对应规则，天然用得上窗口函数与 `generate_series`。
- 月卡生效区间排他，直接防"同一车重复办两张同时在用的月卡"。

### 2.5 功能清单候选（8 项）

车场/车位维护；车辆登记；进出场记录（模拟车牌识别）；自动计费与出场结算；费率规则维护（含生效区间）；月卡办理与核验；收入统计（日/月、临停 vs 月卡）；车位占用率与周转率统计。

### 2.6 演示动线

车位看板（实时颜色）→ 模拟车辆进场（占位）→ 出场（显示时长、免费抵扣、分段金额明细）→ 月卡车辆核验（免计费）→ 调整费率规则 → 日收入统计图与峰值时段热力。

### 2.7 工作量与风险

估算 **12 人日**。风险：费率分段逻辑最容易写错，建议先写纯 SQL 算例（给定入场出场时间 → 期望金额）做单元测试，再接界面。

## 3 候选 C：药房处方调配与药品批次管理系统

### 3.1 场景与背景

医院/校医院药房：处方经医生开立、药师审核后调配发药；药品按批次管理，**近效期先出（FEFO）**；过期药品必须能追溯来源与流向。

### 3.2 角色（3 类 + 患者查询）

医生（开方）、药师（审核、调配、发药）、药房管理员（药品/批次/供应商维护、库存盘点）、患者（查询处方与用药记录）。

### 3.3 表设计（9 张）

| # | 表 | 关键约束 |
| --- | --- | --- |
| 1 | `app_user` | 角色 CHECK（doctor/pharmacist/pharmacy_admin/patient） |
| 2 | `drug_category` | name UNIQUE |
| 3 | `drug` | `price CHECK (price >= 0)`、`is_prescription BOOLEAN` |
| 4 | `supplier` | name UNIQUE、license_no UNIQUE |
| 5 | `drug_batch` | `UNIQUE (drug_id, batch_no)`、`CHECK (quantity >= 0)`、`CHECK (expiry_date > production_date)` |
| 6 | `prescription` | `status CHECK IN ('submitted','reviewed','dispensed','rejected','returned')`、`CHECK (total_amount >= 0)` |
| 7 | `prescription_item` | `CHECK (quantity > 0)`、`CHECK (unit_price >= 0)`；`UNIQUE (prescription_id, drug_id)` |
| 8 | `dispense_record` | 记录处方、药师、时间、发药批次明细 |
| 9 | `stock_movement` | `type CHECK IN ('in','out','adjust','return')`、`CHECK (quantity <> 0)` |

### 3.4 数据库设计亮点

- **库存与流水双轨**：`drug_batch.quantity` 是当前结存，`stock_movement` 是每笔变动。报告可论证：只存结存无法追溯"谁在什么时候发走了哪批药"；只存流水查询慢，所以两者共存并用事务保证一致（可加触发器校验）。
- **FEFO 逐批分配**是全作业最好的 SQL 题：按效期升序累加，用窗口函数算出每批应扣多少，一次查询给出扣减方案：

```sql
WITH need AS (SELECT 12 AS qty),   -- 需要 12 盒
     b AS (
       SELECT id, quantity, expiry_date,
              SUM(quantity) OVER (ORDER BY expiry_date, id) AS cum
       FROM drug_batch
       WHERE drug_id = $1 AND quantity > 0
     )
SELECT id, expiry_date,
       GREATEST(0, LEAST(quantity, (SELECT qty FROM need) - (cum - quantity))) AS take
FROM b
WHERE cum - quantity < (SELECT qty FROM need)
ORDER BY expiry_date;
```

- 效期预警视图（`expiry_date - CURRENT_DATE <= 30`）、过期批次禁止出库（触发器或服务层 + `CHECK`）、处方状态机。

### 3.5 功能清单候选（8 项）

药品/类别/供应商维护；批次入库（效期登记）；效期与库存预警；处方开立；处方审核；调配发药（FEFO 自动选批）；库存盘点与流水查询；统计（药品消耗 Top10、过期损耗、处方量趋势）。

### 3.6 工作量与风险

估算 **15 人日**（SQL 与触发器多）。风险：批次扣减涉及事务与并发，且界面偏表格，20% 界面分要靠预警看板与图表补。

## 4 简版候选

### D 健身房会员课包与团课预约（最小工作量，约 10 人日）

表（6）：member、membership_card、class_schedule、coach、booking、class_package。亮点：`booking UNIQUE(member_id, class_schedule_id)`、课程容量 `CHECK (booked <= capacity)`、课包次数扣减 `CHECK (remaining_sessions >= 0)`、签到与爽约状态。演示直观（选课 + 签到），但数据库深度一般。

### E 期末考场排考与监考冲突检测（约束最硬，界面最弱，约 13 人日）

表（7）：course、exam、exam_room、student、exam_enrollment、invigilator、invigilation_assignment。亮点：三重排他 —— 同一学生同一时段不得两场考试、同一考场同一时段不得两场考试、同一监考同一时段不得两场监考，全部用 `EXCLUDE USING gist (… WITH =, tsrange(…) WITH &&)` 表达。答辩极强，但演示画面只有表格与冲突报告。
