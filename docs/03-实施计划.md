## 4 技术落地方案

### 4.1 环境准备（11/03 前完成，谁缺谁补）

| 项 | 约定 |
| --- | --- |
| 数据库 | PostgreSQL 18（`5432`，Windows 服务 `postgresql-x64-18` 已在运行），库名 `hotel_db`，编码 UTF8，时区 Asia/Shanghai |
| 运行时 | Python 3.12.7（`D:\anaconda3\python.exe`，已装 Django 6.1.2 + psycopg2 2.9.13） |
| 应用 | Django 单进程：`python manage.py runserver 8000`；模板与静态文件由 Django 托管（`DEBUG=True` 即可，演示阶段不配 nginx） |
| 前端资源 | AdminLTE 3.2 官方包（Bootstrap 4.6 + jQuery 3.5.1 + Popper 1.16.1 + FontAwesome 5）拷进 `static/vendor/`，**不用 CDN** |
| 版本管理 | `git init`，主分支 `main`；`.env`、`db.sqlite3`、`__pycache__` 不入库，提供 `.env.example` |
| 演示机 | 只需 PG + 一个 `runserver` 进程；提前准备 `hotel_db` 的 `pg_dump` 备份与一键启动脚本 |

### 4.2 目录与脚本

```
src/                       Django 工程根（manage.py 所在）
├─ manage.py
├─ config/                 settings.py / urls.py / wsgi.py
├─ core/                   业务 app：models / views / forms / services / urls.py / admin.py
├─ templates/              base.html、partials/（head/sidebar/navbar/footer/scripts）、业务页、登录页
└─ static/
   ├─ vendor/adminlte/     AdminLTE 3.2 的 dist/ 与 plugins/
   ├─ css/site.css         中文排版与少量覆盖
   └─ js/site.js
sql/
├─ 01_schema.sql        建表（含 PK/FK/NOT NULL/UNIQUE/CHECK）
├─ 02_constraints.sql   EXCLUDE 排他约束（生成列 during）、部分唯一索引、视图、触发器
├─ 03_seed.sql          房型 5、房间 40、客户 30、预订 60、入住 40（含边界数据）
└─ 04_queries.sql       报告第 4 章 6 条核心 SQL（可直接跑出结果）
```

- `01`–`03` 必须**可重复执行**（`DROP ... IF EXISTS` / `IF NOT EXISTS`），每次改表结构都重跑验证。
- `04_queries.sql` 里的每条 SQL 都要能贴进报告并附执行结果截图。
- Django 侧的表结构以 `sql/01–02` 为准；`manage.py migrate` 只建 `auth` 等内置表，业务表用 `migrations.RunSQL` 执行同一份 DDL，**以脚本为唯一事实来源**。

### 4.3 数据初始化要求

- 主表数据量：房型 ≥5、房间 ≥40、客户 ≥30、预订 ≥60、入住记录 ≥40、支付流水 ≥80。
- 必须包含的边界数据：
  - 同一房间「12-03 退房、12-03 再入住」的记录（验证半开区间 `'[)'` 正确）；
  - 跨月入住（11-28 至 12-02），用于月度营业额拆分；
  - 已取消、未到店各若干，用于取消率统计；
  - 一个「维修中」房间、一个「清洁中」房间，用于房态看板演示；
  - 一条刚被排他约束拒绝的插入（用脚本演示 409 错误，答辩可直接展示）。

## 5 测试与验收

### 5.1 功能验收（每个功能 5 条 DoD）

一个功能算「完成」需同时满足：① 页面可操作；② 表单校验与错误回显齐全（Django Form + `messages`）；③ 数据库约束真实生效（不是模板挡的）；④ 非法输入有中文提示；⑤ 报告中有一张对应截图。

### 5.2 异常用例（对应异常清单 E01–E08）

| 用例 | 操作 | 期望 |
| --- | --- | --- |
| E01 | 离店日期 = 入住日期 | 400，「离店日期必须晚于入住日期」 |
| E02 | 对已预订房间重复预订同区间 | 409，提示冲突日期区间 |
| E03 | 同一客户重复提交同区间 | 409，「请勿重复提交」 |
| E04 | 维修中房间发起预订/入住 | 409，「该房间当前维修中」 |
| E05 | 取消已入住预订 | 409，「已入住订单不可取消」 |
| E06 | 同一预订重复入住/重复结算 | 409，明确状态提示 |
| E07 | 押金不足抵扣 | 结算页提示补收金额 |
| E08 | 删除有引用数据的房型 | 409，提示改为停用 |

**验证方式**：先**绕过页面**用 `psql` 直接 `INSERT` 一条冲突记录，确认被数据库拦下（记录 SQLSTATE `23P01` 与错误原文），再回到页面验证中文提示——两步都要留截图，这是答辩加分点。

### 5.3 SQL 质量

- `F03` 可用房查询、`F09` 入住率查询各跑一次 `EXPLAIN (ANALYZE, BUFFERS)`，确认走了索引，输出存档到 `work/`。
- 核心查询需有支撑索引：`reservation(room_id, check_in_date, check_out_date)` 的 gist 索引（`EXCLUDE` 自动创建）、`reservation(customer_id)`、`check_in_record(reservation_id)`。

## 6 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | `EXCLUDE` 约束漏写 `WHERE` 谓词，历史已退房记录被误判冲突 | 预订全部失败 | 约束必须带 `WHERE (status IN ('pending','confirmed','checked_in'))`；建库后用「已退房同房号同区间」用例回归 |
| R2 | 日期语义不统一（半开/闭区间混用） | 退房当天入住失败或超卖 | 全系统统一 `[check_in, check_out)`；后端封装 `daterange()` 工具函数，禁止散落字符串拼 SQL |
| R3 | 结算规则含糊（提前退房、超时退房） | 金额对不上，报告说不清 | 11/30 前把规则定成表格写进报告 3.2；提前退房按实际天数、超时按加收半天 |
| R4 | 演示数据与房态不一致 | 现场演示穿帮 | 数据只用 `03_seed.sql` 生成，禁止手工改库；每次改约束后重跑种子脚本 |
| R5 | 时间不足（考试周冲突） | 交付不完整 | 砍功能顺序：先砍 F01 区间价格（降为标准价）、再砍增值服务；F03–F07 与统计不可砍 |
| R6 | 本机环境问题（端口占用、口令错） | 现场演示失败 | 11/09 前每人本机跑通一遍；准备 `pg_dump` 备份与一键启动脚本；口令写 `.env` |
| R7 | Django ORM 让 SQL 隐身，报告 4 章没 SQL 可贴 | 数据库 50% 失分 | 约定复杂查询必须 `connection.cursor()` 手写；每个功能验收时检查「SQL 在哪」 |
| R8 | AdminLTE 3.2 基于 Bootstrap 4（已停止维护），与网上的 BS5 教程对不上 | 改样式时踩坑 | 版本锁定 3.2 到 `static/vendor/`，只做少量覆盖，不升级、不追 BS5；布局问题查 [v3.2 官方文档](https://adminlte.io/docs/3.2/) 而不是 BS5 文档 |
