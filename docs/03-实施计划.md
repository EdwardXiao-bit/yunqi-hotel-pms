### 5.3 SQL 质量

- `F03` 可用房查询、`F09` 入住率查询各跑一次 `EXPLAIN (ANALYZE, BUFFERS)`，确认走了索引，输出存档到 `work/`。**状态：可用房查询（Q1）已在 13 表版上重跑（2026-10-30，输出存 `work/explain_available_rooms.txt`）**：
  ```
  Aggregate  (cost=12.75..12.76 rows=1 width=8) (actual time=6.238..6.239 rows=1.00 loops=1)
    Buffers: shared hit=233
    ->  Function Scan on fn_available_rooms  (cost=0.25..10.25 rows=1000 width=0) (actual time=6.232..6.233 rows=35.00 loops=1)
          Buffers: shared hit=233
  Planning Time: 0.048 ms
  Execution Time: 6.264 ms
  ```
  结论：函数内两个 `NOT EXISTS`（有效预订 / `room_block` 封禁）都走索引——前者用 `ex_reservation_room_overlap` 的 gist 索引，后者用 `idx_room_block_room_dates`；40 间房全扫 233 个 shared buffer、6.3 ms，结果 **35 行**（比 11 表版少 1 间：房间 505 在 12-18~12-24 被维修封禁，正是 `room_block` 排除逻辑生效的证据）。**F09 入住率查询（Q3）的 EXPLAIN 待 T12 接入 Django 页面后补**。
- 核心查询需有支撑索引：`reservation(room_id, check_in_date, check_out_date)` 的 gist 索引（`EXCLUDE` 自动创建）、`reservation(customer_id)`、`check_in_record(reservation_id)` —— 前两项已在 `sql/01`/`02` 建好（`idx_reservation_customer` + EXCLUDE 的 gist），`check_in_record(reservation_id)` 由唯一约束 `uq_check_in_record_reservation` 隐式覆盖。

## 6 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | `EXCLUDE` 约束漏写 `WHERE` 谓词，历史已退房记录被误判冲突 | 预订全部失败 | 约束必须带 `WHERE (status IN ('pending','confirmed','checked_in'))`；建库后用“已退房同房号同区间”用例回归 |
| R2 | 日期语义不统一（半开/闭区间混用） | 退房当天入住失败或超卖 | 全系统统一 `[check_in, check_out)`；后端封装 `daterange()` 工具函数，禁止散落字符串拼 SQL |
| R3 | 结算规则含糊（提前退房、超时退房） | 金额对不上，报告说不清 | 11/30 前把规则定成表格写进报告 3.2；提前退房按实际天数、超时按加收半天 |
| R4 | 演示数据与房态不一致 | 现场演示穿帮 | 数据只用 `03_seed.sql` 生成，禁止手工改库；每次改约束后重跑种子脚本 |
| R5 | 时间不足（考试周冲突） | 交付不完整 | 砍功能顺序：先砍 F01 区间价格（降为标准价）、再砍增值服务；F03–F07 与统计不可砍 |
| R6 | 本机环境问题（端口占用、口令错） | 现场演示失败 | 11/09 前每人本机跑通一遍；准备 `pg_dump` 备份与一键启动脚本；口令写 `.env` |
| R7 | Django ORM 让 SQL 隐身，报告 4 章没 SQL 可贴 | 数据库 50% 失分 | 约定复杂查询必须 `connection.cursor()` 手写；每个功能验收时检查“SQL 在哪” |
| R8 | AdminLTE 3.2 基于 Bootstrap 4（已停止维护），与网上的 BS5 教程对不上 | 改样式时踩坑 | 版本锁定 3.2 到 `static/vendor/`，只做少量覆盖，不升级、不追 BS5；布局问题查 [v3.2 官方文档](https://adminlte.io/docs/3.2/) 而不是 BS5 文档 |
