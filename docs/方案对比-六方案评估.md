# 六方案对比评估（选题决策依据）

> 用途：为第 14 组选定课程设计题目的决策文档。
> 前提（已定）：技术栈已定案 **PostgreSQL 18 + Django 6.1 + AdminLTE 3.2（Bootstrap 4.6，服务端模板渲染）**；组内 2 人（胡宇书 组长、肖铭皓）。
> 评分权重来自作业：数据库设计 **50%**、界面设计 **20%**、功能设计 **20%**、异常处理 **10%**；另系统演示占总分 60%。
> 撰写日期：2026-10-29

## 1 结论（先给判断）

**首选：方案四 医院门诊预约管理系统。** 它在「数据库能拿分」与「现场演示好看」之间平衡最好：号源扣减/恢复、排班唯一约束、患者同一时段不得重复预约都能用 PostgreSQL 的 `CHECK` + 部分唯一索引 + `EXCLUDE` 约束在**数据库层**直接表达，答辩时是硬货；同时挂号流程（选科室 → 选医生 → 选日期 → 选时段 → 确认）天然是个有画面感的交互，2 人 6 周做得完。

**次选（数据库上限最高）：方案六 酒店房间预订与入住。** `EXCLUDE USING gist (room_id WITH =, daterange(check_in, check_out, '[)') WITH &&)` 这一条约束能同时镇住「同一房间重叠日期不得重复预订」，是整个作业里最能体现「你懂数据库」的设计；代价是日期边界、多晚结算、房态流转细节多，工作量比方案四高一档。

**最稳（工作量最小）：方案三 图书借阅。** 部分唯一索引 `WHERE return_time IS NULL` 直接实现「已借出的副本不得重复借出」，约束漂亮、代码量小；缺点是界面朴素、演示画面感弱，20% 的界面分吃不满。

**不推荐给 2 人组：方案五 外卖。** 它要 4 类角色（用户/商家/配送员/管理员）各一套界面，状态线最长，工作量在六个方案里最大，6 周内做完整容易翻车。

## 3 逐方案详解

### 方案一 电商订单管理系统

- **规模**：9 张表（user, category, product, cart, cart_item, orders, order_item, inventory, payment），表最多但职责清楚。
- **数据库加分点**：`CHECK (stock >= 0)`；`cart_item UNIQUE(cart_id, product_id)`；订单明细保存**下单时单价快照**（`order_item.unit_price`）—— 这是「为什么不在订单里 JOIN 当前价格」的好论点；`orders.total_amount` 可用触发器/生成列与明细保持一致的讨论。
- **PG 特性**：`UPDATE inventory SET stock = stock - $1 WHERE product_id = $2 AND stock >= $1` 返回影响行数判断扣减是否成功，配合事务讲并发与超卖，答辩非常好讲。
- **演示观感**：好（商品列表、购物车、下单、后台）。
- **工作量**：高 —— 商品/分类/库存/购物车/订单/支付 6 组页面。
- **坑**：支付只能模拟；表多容易在报告 3.2.2 里写不完。

### 方案二 学生选课管理系统

- **规模**：8 张表，且必须区分「课程 course」与「教学班 teaching_class」。
- **数据库加分点**：`enrollment UNIQUE(student_id, teaching_class_id)`（不得重复选）、`CHECK (score BETWEEN 0 AND 100)`、教学班容量 `CHECK (0 <= enrolled_count AND enrolled_count <= capacity)`。
- **PG 特性**：容量校验要行锁（`SELECT ... FOR UPDATE`）或触发器；`AVG(score)` + `RANK() OVER` 排名。
- **演示观感**：一般 —— 全是表格 CRUD，缺少「操作流程」的画面。
- **工作量**：中。
- **坑**：学生/教师/管理员三角色功能差异大，页面多但都长得像表格。

### 方案三 图书借阅管理系统

- **规模**：7 张表，核心是 `book`（书目）与 `book_copy`（馆藏副本）的一对多 —— 这个区分本身就是报告 3.2.1 的论述点。
- **数据库加分点**：`book_copy.copy_code UNIQUE`；`borrow_record CHECK (return_time IS NULL OR return_time >= borrow_time)`；**部分唯一索引**：
  ```sql
  CREATE UNIQUE INDEX uq_copy_active_borrow
      ON borrow_record (book_copy_id) WHERE return_time IS NULL;
  ```
  一条索引即保证「同一副本不能同时有两条未归还记录」，把业务规则下沉到数据库 —— 异常处理 10% 和数据库 50% 都能吃到分。
  预约同理：`CREATE UNIQUE INDEX ... ON reservation (reader_id, book_id) WHERE status = 'active'`。
- **PG 特性**：逾期天数 `CURRENT_DATE - due_date`；Top10 借阅量用 `RANK() OVER`。
- **演示观感**：弱 —— 列表 + 表单，读者端可做检索与预约，但仍偏静态。
- **工作量**：中低（六个方案里第二省事）。
- **坑**：要造 100+ 副本数据演示才不空；界面分吃不满。

### 方案四 医院门诊预约管理系统 ★首选

- **规模**：7 张表（patient, doctor, department, schedule, appointment, visit_record，clinic_room 可选）。
- **数据库加分点**：
  - `schedule UNIQUE(doctor_id, work_date, time_slot)` —— 一个医生同时段只能有一个排班；
  - `CHECK (booked_count >= 0 AND booked_count <= max_quota)` —— 号源上限在库层兜底；
  - `appointment UNIQUE(patient_id, schedule_id)` —— 同一患者不得重复预约同一时段；
  - **跨排班的时段冲突**可用 PostgreSQL 排他约束表达（报告里作为进阶设计写）：
    ```sql
    ALTER TABLE appointment ADD CONSTRAINT ex_patient_overlap
        EXCLUDE USING gist (
            patient_id WITH =,
            tsrange(slot_start, slot_end) WITH &&
        ) WHERE (status IN ('booked', 'arrived'));
    ```
  - 状态机：`CHECK (status IN ('booked','arrived','completed','cancelled','no_show'))`。
  - 取消恢复号源：事务内 `UPDATE schedule SET booked_count = booked_count - 1`，与「号源满不得继续预约」构成一对反向操作，异常处理章节好写。
- **演示观感**：好 —— 挂号是所有人都理解的流程，五个步骤点下来有节奏；医生端「今日预约名单 + 写就诊记录」形成闭环。
- **工作量**：中 —— 排班用脚本批量生成，不必做日历组件；核心页面约 6–8 个。
- **坑**：日期/时区处理；号源并发（演示单机无压力，但报告要写 `FOR UPDATE`）；排班数据要提前造。

### 方案五 简化版外卖订单管理系统

- **规模**：10 张表，六个方案里最多。
- **数据库加分点**：`order_item` 单价快照 + `orders.total_price`；配送时间统计
  `AVG(EXTRACT(EPOCH FROM delivered_at - accepted_at))`；多状态时间戳（商家接单、配送接单、送达）本身是很好的状态设计素材。
- **PG 特性**：每日订单量与营业额 `date_trunc('day', created_at)`；平均配送时长。
- **演示观感**：好，但**要来回切账号**（用户下单 → 商家接单 → 骑手配送 → 用户评价），演示节奏容易乱。
- **工作量**：最高 —— 4 类角色 × 各自界面。
- **坑**：2 人 6 周做完整风险最高；`review` 可选表建议直接砍掉。

### 方案六 酒店房间预订与入住管理系统

- **规模**：8 张表（customer, room_type, room, reservation, check_in, payment，service/service_order 可选）。
- **数据库加分点（全场最高）**：
  ```sql
  ALTER TABLE reservation ADD CONSTRAINT ex_room_no_overlap
      EXCLUDE USING gist (
          room_id WITH =,
          daterange(check_in, check_out, '[)') WITH &&
      ) WHERE (status <> 'cancelled');
  ```
  一条约束解决「同一房间在重叠日期内不得重复预订」，且 `'[)'` 半开区间正确处理「上午退房、当天下午入住」的边界 —— 这是最能在答辩里拉开差距的一条。配合 `CHECK (check_out > check_in)`、房态枚举 `available/reserved/occupied/cleaning/maintenance`。
- **PG 特性**：`daterange` 类型、`&&` 重叠运算、`generate_series` 造日历、入住率 = 占用房夜 / 可售房夜。
- **演示观感**：好 —— 日历选房 + 房态看板，比图书/选课有画面。
- **工作量**：中高 —— 房型/房间/预订/入住/退房/结算/房态 7 个动作，且结算涉及多晚金额。
- **坑**：日期区间边界（半开/闭区间）、跨月统计、退房后清洁态回收；表之间状态耦合多，改动牵一发动全身。

## 4 PostgreSQL 特性 × 方案匹配

| 特性 | 能吃满的方案 | 说明 |
| --- | --- | --- |
| 部分唯一索引 `WHERE ...` | 三、四 | 图书「未归还副本唯一」、门诊「预约有效状态唯一」 |
| `EXCLUDE` + range 类型 | 六（最强）、四 | 酒店日期重叠、门诊患者时段重叠 |
| `CHECK` 约束 | 全部 | 库存、容量、号源、分数、状态枚举 |
| `date_trunc` / `generate_series` | 一、四、五、六 | 月度统计、未来 7 天号源、日历 |
| 行锁 `SELECT ... FOR UPDATE` | 一、二、四、六 | 扣库存 / 抢号源 / 占房 |
| 窗口函数 `RANK() OVER` | 全部 | Top10 商品/图书/医生/房型 |

结论：既然技术栈已定 PostgreSQL，**选一个能把 EXCLUDE 或部分唯一索引用上的方案，才算不浪费这个选型**。方案四两者都能用（部分唯一索引 + 时段排他），这是它排第一的技术理由。
